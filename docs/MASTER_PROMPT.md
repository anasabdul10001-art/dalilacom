# MASTER PROMPT — DALILACOM Android App (النسخة الموحدة النهائية)

أريد منك بناء تطبيق Android حقيقي واحترافي باسم:

**دليلكم — DALILACOM**

وهو تطوير حديث لمشروع دليلكم الذي كان قائمًا سابقًا على نظام بطاقة الحسم، ولكن في النسخة الجديدة لا نريد أي بطاقة بلاستيكية أو بطاقة حقيقية.

التطبيق نفسه سيكون هو البطاقة الرقمية للمستخدم، وفي نفس الوقت سيكون منصة تجمع العملاء والتجار والمتاجر والعروض والخصومات.

أريد منك التعامل مع المشروع كمنتج SaaS / Marketplace حقيقي قابل للإطلاق، وليس مجرد Prototype أو تصميم واجهات.

## 1. فكرة المشروع الأساسية

دليلكم منصة تجمع بين:

**المستخدم العادي**

المستخدم يستطيع:
- إنشاء حساب.
- الاشتراك في عضوية دليلكم.
- امتلاك بطاقة حسم رقمية داخل التطبيق.
- الحصول على كود/QR Code رقمي متغير.
- استخدام العضوية لدى التجار المشتركين.
- البحث عن التجار والمتاجر.
- مشاهدة نسبة الحسم التي يقدمها كل تاجر.
- مشاهدة عنوان التاجر.
- الاتصال بالتاجر.
- مراسلة التاجر عبر Chat.
- مشاهدة منتجات التاجر.
- شراء المنتجات من داخل التطبيق.
- شراء منتجات مع حسم أو بدون حسم حسب المنتج والتاجر.
- مشاهدة سجل عمليات الحسم والطلبات.

لا يوجد أي اعتماد على بطاقة بلاستيكية. الهاتف والتطبيق هما البطاقة.

## 2. نظام العضوية والحسم

عند اشتراك المستخدم في العضوية، يصبح لديه **Digital Discount Membership** داخل التطبيق، يظهر له:
- اسم المستخدم، صورة الحساب.
- حالة العضوية، تاريخ بداية العضوية، تاريخ انتهاء العضوية.
- رقم عضوية داخلي.
- QR Code ديناميكي.
- كود مؤقت يمكن استخدامه كبديل للـQR.

**مهم جدًا:** لا تجعل QR Code ثابتًا يمكن تصويره وإرساله لشخص آخر. يجب أن يكون الكود **Dynamic / Temporary / Server Validated**، ويتغير بشكل دوري (آلية نهائية بالقسم 62).

عندما يقوم التاجر بمسح الكود، يتحقق التطبيق من السيرفر من:
1. المستخدم موجود.
2. العضوية فعالة.
3. الكود صالح.
4. الكود لم تتم إعادة استخدامه بطريقة غير مسموحة.
5. التاجر هو تاجر مسجل.
6. التاجر يملك صلاحية تقديم الحسم.
7. العرض/الحسم ما زال فعالًا.

ثم تظهر عملية تأكيد الحسم.

## 3. حساب التاجر

التاجر ليس مجرد مكان يظهر على الخريطة، بل لديه Merchant Account كامل، يدير فيه:

**الملف التجاري:** اسم المتجر/الشركة، الشعار، صور المتجر، وصف النشاط، التصنيف، العنوان، الموقع الجغرافي، رقم الهاتف، WhatsApp، أوقات العمل، وسائل التواصل، روابط التواصل الاجتماعي، معلومات إضافية.

## 4. نظام الحسم الخاص بالتاجر

كل تاجر يستطيع تحديد نسبة الحسم (10%، 15%، 20%...)، ويمكن أن يكون الحسم:
- على كامل المنتجات.
- على منتجات معينة فقط.
- على خدمات معينة.
- عرض لفترة محددة.
- عرض محدود العدد.

مثال: "خصم 15% على جميع منتجات المتجر لمشتركي دليلكم" أو "خصم 20% على هذا المنتج فقط."

---

## 5. المتجر الإلكتروني داخل التطبيق

كل تاجر يجب أن يستطيع إنشاء متجر إلكتروني داخل DALILACOM، يضيف فيه: المنتجات، صور المنتجات، اسم المنتج، الوصف، السعر، السعر بعد الخصم، المخزون، SKU، التصنيف، خيارات المنتج (مقاسات، ألوان)، المنتجات المتاحة/غير المتاحة.

ويحدد لكل منتج هل يوجد حسم لمشتركي دليلكم (YES/NO). مثال:
- منتج A: السعر €100، سعر العضو €85، خصم 15%.
- منتج B: السعر €50، حسم العضوية غير متوفر.

## 6. البيع داخل التطبيق

يجب أن يكون هناك: Cart، Orders، Order Details، Order Status (Pending, Confirmed, Preparing, Shipped, Delivered, Cancelled).

## 29. اللغات (Multi-Language Support)

التطبيق يدعم **3 لغات** من الإصدار الأول: **العربية (RTL)**، **الألمانية (LTR)**، **الإنجليزية (LTR — Fallback افتراضي)**.

**تحديد اللغة:**
1. تلقائيًا حسب لغة الجهاز (Device Locale) عند أول فتح.
2. اختيار يدوي من المستخدم بأي وقت (Settings/Onboarding)، يُحفظ بحساب المستخدم (مو محليًا بالجهاز بس).

**التأثير على التصميم:**
- كل النصوص الثابتة بملفات ترجمة منفصلة (Localization Files)، لا نصوص Hardcoded.
- الاتجاه يتغيّر تلقائيًا RTL/LTR (النصوص، الأيقونات، ترتيب العناصر).
- **بيانات التاجر والمنتجات متعددة اللغات** (قرار نهائي): كل حقل قابل للترجمة يُصمَّم كجدول ترجمة منفصل (Translation Table)، مثلًا `Product` + `ProductTranslations {productId, languageCode, name, description}` — نفس المبدأ لـ MerchantProfile, Store, Category, Discount/Offer.
- لكل تاجر **لغة أساسية (Primary Language)** يكتب فيها أول محتوى، وباقي اللغات اختيارية إضافية.
- **Fallback عند نقص الترجمة:** عرض المحتوى بلغة التاجر الأساسية مع وسم "غير مترجم".
- واجهة التاجر لإدخال الترجمات: تبويبات لغات (🇸🇾 عربي | 🇩🇪 ألماني | 🇬🇧 إنجليزي) لكل منتج/بيانات متجر.
- الإشعارات والرسائل من السيرفر (SMS/Email) تُرسَل بلغة المستخدم المحفوظة.

### قاعدة مهمة جدًا

أنا أريد مشروعًا حقيقيًا قابلًا للتشغيل. لا أريد: Fake buttons، Fake API، Fake database، Static products، Hardcoded users، Hardcoded discounts، Mock QR validation. إذا لم يتم تنفيذ جزء معين بعد، اذكر ذلك بوضوح ولا توهمني أنه يعمل. كل Feature يجب أن تكون مرتبطة بالـBackend والـDatabase عندما نصل لمرحلة تنفيذها.

### أسلوب العمل

اعمل معي خطوة بخطوة. لا تنتقل لFeature جديدة قبل التأكد أن السابقة تعمل. عند تعديل أي كود موجود: افحص الكود الحالي أولًا، لا تحذف Features بدون سبب، لا تعيد كتابة المشروع من الصفر، حافظ على Architecture، أصلح المشاكل بدل الالتفاف حولها، اشرح ما الذي تغيّر، اذكر الملفات المعدّلة، اذكر Dependencies جديدة، اذكر أوامر التشغيل والاختبار. إذا أعطيتك Repository أو ملفات موجودة، اعتبرها المصدر الحقيقي وحلّلها قبل أي قرار معماري.

### أهم مبدأ بالمشروع

DALILACOM ليس تطبيق بطاقة حسم فقط. هو: **Digital Membership + Discount Platform + Merchant Marketplace + E-commerce + Social Layer**. المستخدم يحصل على عضوية رقمية، التاجر يحصل على حساب تجاري ومتجر إلكتروني، والمنصة تربط الطرفين بنظام حسم رقمي آمن، بالإضافة لطبقة تفاعل اجتماعي (متابعة، تعليقات، لايك، مشاركة).

**ابدأ الآن بالمرحلة الأولى:** Analyze the project and propose the complete technical architecture, technology stack, database structure, user roles, and application structure before writing implementation code.

## 31. اكتشاف الخصومات حسب الموقع والتصنيف

عند أول فتح، يحدد الزبون موقعه (Location Permission)، وبناءً عليه:
- المحلات الأقرب له جغرافيًا (Nearest First).
- تكبير/تصغير نطاق البحث حوله (Radius Selector: 1كم، 5كم، 10كم، أو يدوي).
- اختيار تصنيف بدل الاعتماد على القرب فقط، مثلًا "أطباء" ثم فلترة حسب الاختصاص (أسنان، جلدية...)، أو "ملابس رجالية".

قائمة التصنيفات شاملة تقريبًا لكل مناحي الحياة (تصنيفات هرمية — رئيسية + فرعية): مطاعم وأغذية، ملابس (رجالي/نسائي/أطفال)، صالونات حلاقة وتجميل، نوادي رياضية، أطباء بكل الاختصاصات، صيدليات، تعليم ودورات، سيارات وصيانة، عقارات، سياحة وفنادق، خدمات منزلية، إلكترونيات وموبايلات.

## 32. تفاصيل الرابط بين المحل والحسم

كل محل ممكن يكون عنده أكتر من نوع حسم بنفس الوقت، ولازم الزبون يشوف بوضوح:
- نسبة الحسم بالضبط.
- على شو منطبق (كامل الفاتورة أو خدمة/منتج معيّن).
- إذا في أكتر من حسم، تظهر كل حسم لحاله بوضوح (مثال: حلاقة رجالي 5%، خدمات تجميل 10%).

عند فتح صفحة المحل، تظهر قائمة بكل الحسومات المتوفرة مع توضيح كل حسم على شو منطبق.

---

## 33. البحث المرتبط بالموقع والتصنيف

البحث النصي يرجع نتائج مرتبة حسب الأقرب أولًا. فلترة إضافية: حسب التصنيف، نسبة الحسم، المسافة. خيار توسيع/تضييق نطاق البحث الجغرافي من نفس شاشة النتائج. يدعم البحث الصوتي (القسم 78).

---

## 34. سجل عمليات الحسم (Discount Log) عند الأطراف الثلاثة

كل عملية حسم فعلية تُسجَّل وتظهر بشكل واضح ومتطابق عند: الزبون، صاحب المحل، الأدمن — بمصدر واحد للحقيقة (Single Source of Truth)، وتشمل: اسم المحل، قيمة الفاتورة الأصلية، نسبة الحسم، مبلغ الحسم، المبلغ النهائي، تاريخ ووقت العملية، رقم العملية (Transaction ID).

- **عند الزبون:** سجل حسوماته الخاص.
- **عند المحل:** لوحة التاجر، لمتابعة ومحاسبة كل الحسومات المقدَّمة.
- **عند الأدمن:** Discount Transactions كاملة لكل المنصة.

تعكس فقط العمليات الفعلية المؤكدة (Confirmed)؛ المحاولات الملغاة تظهر بحالة منفصلة وواضحة (Cancelled/Failed).

---

## 35. أنواع حسم إضافية يحددها صاحب المحل بنفسه

بالإضافة للنسبة العادية، يقدر التاجر يضيف:
- **حسم محدود بعدد مرات الاستخدام لكل زبون** (مثال: خصم 20% لأول 3 زيارات فقط).
- **عرض مجاني محدود العدد** (مثال: قهوة مجانية كل 5 زيارات).

قابلة للتحرير من صاحب المحل: نوع العرض، عدد المرات المسموحة، هل العداد لكل زبون منفرد أو للمحل ككل، تاريخ بداية/نهاية اختياري.

**قاعدة مهمة:** السيرفر (Backend) هو المسؤول عن عدّ مرات الاستخدام والتحقق منها عند كل مسح QR — لا ثقة بأي عداد محلي.

---

## 36. تعديل الملف الشخصي (Self-Editable Profiles)

**الزبون:** الاسم، الصورة، الهاتف، البريد، كلمة المرور، العناوين المحفوظة.

**التاجر:** كل بيانات الملف التجاري (القسم 3)، تفاصيل الحسومات والعروض (القسم 4، 35)، بيانات المنتجات (القسم 5).

**قاعدة:** التعديلات الحساسة (تصنيف رئيسي، موافقة أولى) تحتاج مراجعة الأدمن؛ التعديلات غير الحساسة (صور، أوقات عمل، أوصاف، منتجات) تنعكس مباشرة. كل تعديل يُسجَّل بـ AuditLogs.

### 36.1 إخفاء معلومات معينة عن العامة (Privacy Toggle)

بجانب كل حقل عام (الهاتف، واتساب، البريد، مواقع التواصل، العنوان بالتفصيل)، مفتاح تبديل: 👁️ ظاهر للعامة / 🚫 مخفي. الزبون يقدر يخفي صورته/اسمه الكامل بالتفاعلات العامة. التاجر يقدر يخفي رقم هاتف معيّن أو موقعه الدقيق. **معلومات لا يجوز إخفاؤها:** حالة العضوية، موافقة التاجر بالمنصة، نسبة الحسم — القائمة تُحدَّد Backend، لا حرية كاملة للمستخدم.

---

## 37. متابعة المحلات (Follow System)

زر "متابعة/إلغاء متابعة" بصفحة كل محل (متل إنستغرام). قسم **"المحلات اللي بتابعها"** (Following). إشعار تلقائي للمتابعين عند نشر منتج/عرض جديد. قسم "جديد من المحلات اللي بتابعها" بالـHome. عدد المتابعين مؤشر لترتيب "Featured Stores". نظام مستقل تمامًا عن العضوية والحسم.

---

## 38. المفضلة (Favorites)

زر ⭐/❤️ "إضافة للمفضلة" على صفحة المحل وعلى أي منتج. قسم "المفضلة" بالبروفايل (تبويبين: محلات، منتجات). الفرق عن المتابعة: مفضلة = حفظ سريع/Wishlist بدون التزام إشعارات.

---

## 39. التعليقات (Comments) — بطابع سوشال ميديا

تحت المنتجات وصفحات المحلات: تعليق نصي، إرفاق صورة اختياري، Like 👍، رد متفرّع (Nested — يشمل رد رسمي من التاجر)، وقت وتاريخ.

**الإشراف:** إبلاغ (Report)، حذف الأدمن من لوحة التحكم، إخفاء التاجر عند نفسه فقط (لا حذف نهائي)، Rate Limiting ضد السبام.

**العلاقة بالتقييم:** مستقلان لكن مرتبطان؛ تعليقات الشراء الموثّق (Verified Purchase) تُميَّز بعلامة خاصة.

---

## 40. الحظر (Block)

زر "حظر" متاح من صفحة المحل، الـChat، أو قوائم المتابعة، لأي طرف (زبون/تاجر). عند الحظر: إلغاء المتابعة تلقائيًا، منع فتح/إكمال Chat، منع التعليق/اللايك، (اختياري للتاجر) منع الحسم أيضًا. "إلغاء الحظر" متاح بسهولة. يُسجَّل بـAuditLogs، لا يظهر للطرف الآخر بشكل صريح. لا يأثر على حساب المستخدم ككل (شغل الأدمن فقط عبر القسم 57).

---

## 41. زر الإعجاب (Like/Heart) — تصميم مميز

قلب ❤️ (SVG/Icon مخصص، لا Emoji جاهز) بدل الإبهام بمعظم الأماكن، بانسجام مع القسم 39 و38. أنيميشن Bounce عند الضغط، Primary Red عند التفعيل، Outline رمادي عند عدم التفعيل. عداد إعجابات واضح وغير مزعج. نفس الشكل يُستخدم بالمفضلة كمان — "قلب أحمر ممتلئ = مفضّل" باتساق كامل.

---

## 42. نظام نقاط الولاء (Loyalty Points)

كل عملية حسم فعلية تمنح نقاط (بنسبة يحددها الأدمن). شاشة "نقاطي": الرصيد، سجل الاكتساب، طرق الاستبدال (خصم إضافي، شهر عضوية مجاني، منتج/خدمة مجانية). التاجر يقدر يقدّم مكافآت خاصة بمتجره. كل عملية تُتحقق من السيرفر.

---

## 43. نظام الإحالة (Referral System)

كل زبون يملك كود دعوة فريد. لما يسجّل مستخدم جديد بالكود ويستخدم أول حسم فعلي، الاثنان ياخدو مكافأة (نقاط، أيام عضوية، خصم). شاشة "دعوة الأصدقاء": الكود، عدد المدعوين، عدد المكافآت. شرط تفعيل: استخدام حسم فعلي (مو مجرد تسجيل).

---

## 44. التحدي الشهري (Monthly Streak/Challenge)

تحديات دورية يحددها الأدمن (مثال: "استخدم الحسم 3 مرات هالشهر = 50 نقطة إضافية"). شريط تقدّم بصفحة "نقاطي" أو بالـHome. إشعار تلقائي عند إكمال التحدي.

---

## 45. إحصائيات للتاجر (Merchant Analytics)

لوحة إحصائيات خاصة بالتاجر: عدد زيارات صفحته، عدد استخدامات الحسم (Chart)، أوقات الذروة، المنتجات الأكثر مبيعًا/مشاهدة، عدد المتابعين/المفضّلين الجدد.

---

## 46. عروض مؤقتة بطابع Story (Story-Style Offers)

عرض سريع 24-48 ساعة، يظهر كـ"ستوري" دائري بأعلى الـHome (متل إنستغرام)، يختفي تلقائيًا بعد انتهاء المدة. يخلق إحساس استعجال، قابل للربط بعداد استخدام محدود.

---

## 47. عروض ممولة/مميزة (Boost / Promoted Listing)

التاجر يدفع ليظهر محله بمرتبة أعلى ضمن تصنيف أو "Featured Stores" لفترة محددة، مع وسم واضح "إعلان مموّل/Sponsored". الأدمن يتحكم بعدد الأماكن الممولة. مصدر دخل إضافي منفصل عن اشتراك العضوية.

---

## 48. الأكثر رواجًا بمنطقتك (Trending Near You)

قسم بالـHome يعرض الأكثر استخدامًا فعليًا (بيانات استخدام حقيقية فقط، مش تحرير يدوي ولا إعلان مدفوع) بمنطقة الزبون خلال فترة قريبة.

---

## 49. قوائم منسّقة (Collections)

الأدمن (ومستقبلًا Editors) يسوّي قوائم مواضيعية جاهزة ("أفضل 10 مطاعم بدمشق")، قابلة للمشاركة كرابط مستقل، تستخدم كأداة تسويقية.

---

## 50. المشاركة خارج التطبيق (Share)

زر مشاركة 📤 على أي محل/منتج/عرض/Collection، يولّد رابط مباشر (Deep Link) أو صورة جاهزة للمشاركة. غير المسجّل يفتح صفحة المحتوى مباشرة أو صفحة تحميل التطبيق.

---

## 51. المحفظة الرقمية (Wallet)

قسم موحّد "محفظتي": نقاط الولاء، كوبونات فعالة، رصيد كاش باك (مستقبلًا)، مكافآت الإحالة، بطاقات الهدايا (القسم 80). يُبنى كـAbstraction/Interface قابل للتوسع.

---

## 52. نظام الأفلييت (Affiliate System) — تسويق بنسبة عمولة

مستقل عن الإحالة العادية (القسم 43). أي مستخدم يتقدّم ليصير **Affiliate** (يحتاج موافقة الأدمن). بعد الموافقة: رابط/كود فريد + Affiliate Dashboard.

**الهدف:** جذب تجار جدد (عمولة عند الاشتراك والتفعيل) و/أو جذب زبائن جدد (عمولة عند اشتراك عضوية مدفوعة).

**العمولة:** نسبة مئوية يحددها الأدمن، تختلف حسب **مستويات الأفلييت (Tiers)** قابلة للإدارة. تُحسب وتُتحقق من السيرفر فقط.

**Dashboard:** الزيارات (Clicks)، التسجيلات الفعلية (Conversions)، إجمالي العمولات، حالة كل عمولة (Pending → Approved → Paid)، سجل تفصيلي.

**السحب:** بعد حد أدنى (Minimum Payout)، مبني كـAbstraction قابل لربط وسيلة دفع حقيقية لاحقًا.

**لوحة الأدمن:** قائمة الأفلييتز وحالتهم ونسبهم، الموافقة على الطلبات، الموافقة على صرف العمولات، تقارير أداء.

**جداول DB مستقلة:** `Affiliates`, `AffiliateClicks`, `AffiliateConversions`, `AffiliateCommissions`.

---

## 53. سلايدات وبانرات إعلانية مدفوعة (Paid Banners/Slider Ads)

مساحة إعلانية بأعلى الـHome (سلايدر/Carousel). التاجر يرفع: صورة البانر، رابط الوجهة، المدة. يدفع، ويدخل الطلب بحالة **Pending Review**.

**دورة القبول:** رفع + دفع → Pending → مراجعة الأدمن (محتوى مناسب + تأكيد الدفع فعليًا) → Scheduled/Active (يظهر تلقائيًا بالتاريخ المحدد) أو Rejected (مع إشعار وسبب + آلية استرجاع/رصيد). ينتهي تلقائيًا بعد المدة.

**قاعدة مهمة:** لا يظهر أي بانر للعامة قبل تأكيد الدفع والمحتوى سوا.

### 53.1 إدارة البانر يدويًا من الأدمن/الموظف

الأدمن يقدر يوقف أي بانر نشط يدويًا قبل انتهاء مدته (مخالفة، شكوى)، مع تسجيل السبب وإشعار التاجر. سؤال سياسة مفتوح: استرجاع جزئي (Pro-rated Refund) للمدة المتبقية أو لا.

---

## 54. طرق الدفع — تشمل الدفع النقدي (Cash) كمان

بالإضافة للإلكتروني (محافظ، بطاقات، تحويل بنكي — القسم 24)، النظام يدعم **دفع نقدي (Cash) بموافقة يدوية**: التاجر/الزبون يدفع نقدًا، والأدمن يؤكد يدويًا من لوحة التحكم قبل تفعيل الخدمة.

**حالة الدفع (Enum):** `Pending` / `Paid — Cash (Manual Confirmation)` / `Paid — Online` / `Failed` / `Refunded`.

نظام الدفع (Abstraction — القسم 24) يدعم أكتر من "مزود" بنفس الوقت: مزود إلكتروني حقيقي + مزود يدوي (Cash) يديره الأدمن. يدعم أيضًا **الدفع عند الاستلام (COD)** للمتجر الإلكتروني (تفصيل بالقسم 59.4).

---

## 55. نظام صلاحيات الموظفين (Staff/Admin Roles — RBAC)

Super Admin ينشئ حسابات **موظف (Staff Account)** بصلاحيات محددة حسب المهمة:
- مراجعة البانرات، دعم التجار، خدمة الزبائن، المحاسبة/الدفع...

**وحدات صلاحيات مستقلة:** إدارة المستخدمين، التجار والموافقة، المنتجات/المتاجر، الحسومات والعروض، البانرات، المدفوعات، الأفلييت، التصنيفات، الإشراف على التعليقات/البلاغات، الاطلاع على الإحصائيات (View Only).

كل عملية موظف تُسجَّل بـAuditLogs باسمه الشخصي. Super Admin وحده ينشئ/يحذف حسابات الموظفين ويعدّل صلاحياتهم.

---

## 56. استعادة كلمة المرور (Forgot Password)

زر "نسيت كلمة المرور؟" بشاشة تسجيل الدخول لكل الأدوار. OTP أو رابط إعادة تعيين صالح لفترة محددة (10 دقائق) عبر إيميل/SMS. بعد التغيير، تنتهي كل الجلسات القديمة تلقائيًا.

**أمان:** Token Expiration، Rate Limiting ضد Brute Force، عدم كشف وجود الحساب من عدمه برسالة الخطأ.

---

## 57. قسم إدارة المستخدمين بالتفصيل (Admin — User Management)

**عرض:** كل بيانات البروفايل، حالة العضوية، سجل الحسم الكامل، سجل الطلبات، المتابَعات والمفضلة، سجل التعليقات/البلاغات، النقاط والمحفظة.

**عمليات الأدمن:**
- **تعديل** أي حقل يدويًا.
- **إعادة ضبط:** كلمة المرور، رمز/QR العضوية عند اشتباه، بعض العدادات بحالات استثنائية.
- **حظر/إيقاف:** مؤقت أو دائم، مع إلغاء الجلسات النشطة فورًا.
- **حذف الحساب:** Soft Delete يُفضَّل (يحافظ على سجل العمليات القديمة).

كل عملية تُسجَّل بـAuditLogs (اسم المنفّذ، الوقت، السبب). الحظر/التعديل لا يأثر تلقائيًا على عمليات حسم سابقة موثّقة.

---

## 58. قسم المحاسبة الكامل (Full Accounting Module)

قسم "المحاسبة" مستقل بلوحة الأدمن.

**58.1 مصادر الإيرادات (تلقائية):** اشتراكات العضوية، البانرات المدفوعة، عروض Boost، ومصادر مستقبلية (Extensible Revenue Types).

**58.2 المصاريف (يدوية):** التصنيف (رواتب، استضافة، تسويق، عمولات أفلييت، تشغيلية، أخرى)، القيمة، التاريخ، الوصف، مرفق اختياري. قابلة للتعديل/الحذف (بـAuditLogs)، وتصنيفات قابلة للإضافة من الأدمن.

**58.3 حساب الأرباح:** الربح = الإيرادات − المصاريف، ضمن: يومي، أسبوعي، شهري، سنوي، أو **فترة مخصصة (من-إلى)**.

**58.4 العرض والتقارير:** Dashboard مالي (إجمالي إيرادات/مصاريف/صافي ربح + مقارنة بالفترة السابقة)، Charts (إيرادات مقابل مصاريف، توزيع المصاريف)، جدول تفصيلي قابل للفرز، تصدير Excel/PDF.

**58.5 سؤال محاسبي مفتوح:** Cash Basis (تاريخ استلام الدفعة) مقابل Accrual Basis (توزيعها على أشهر الخدمة) للاشتراكات السنوية — يجب حسمه بمرحلة التصميم.

**أمان:** الوصول محصور بـSuper Admin أو موظف محاسبة مخوّل فقط (القسم 55).

---

## 59. نظام المتجر الإلكتروني بأسلوب أمازون (Amazon-Style E-commerce Logic)

**59.1 المخزون:** تحديث لحظي. إشعار "مخزون منخفض" عند حد أدنى. عند الصفر: المنتج يبقى ظاهر بحالة "غير متوفر" (لا يختفي، زي أمازون)، مع زر اختياري "أعلمني عند التوفر". لا Backorder بالمرحلة الأولى.

**59.2 خيارات المنتج (Variants):** Parent Product (بيانات مشتركة) + `ProductVariants` مستقلة (SKU، سعر، مخزون، صور اختيارية) لكل تركيبة مقاس/لون. الزبون يختار من Dropdown/أزرار بصفحة المنتج.

**59.3 الشحن:** كل تاجر مسؤول عن توصيله بنفسه (Merchant-Managed Shipping) — مناطق التوصيل، السعر لكل منطقة، مدة التوصيل التقريبية، تُحسب تلقائيًا وتظهر قبل التأكيد النهائي.

**59.4 الدفع:** أونلاين + Cash on Delivery (COD كافتراضي بالمرحلة الأولى)، مع إمكانية للتاجر يحدد قبول COD لمنطقة معينة أو لا.

**59.5 سلة متعددة التجار:** السلة تسمح منتجات من أكتر من تاجر، وعند Checkout تنقسم تلقائيًا لـSub-Orders مستقلة لكل تاجر (رقم طلب، حالة تتبع، تكلفة توصيل خاصة بكل واحدة)، تظهر مجمّعة بشاشة "طلباتي".

**59.6 الإلغاء والاسترجاع:** إلغاء الزبون مسموح قبل الشحن فقط. إلغاء التاجر مسموح قبل الشحن بسبب مكتوب. طلب استرجاع بعد التسليم خلال مدة محددة، موافقة/رفض التاجر، وتدخل الأدمن كوسيط عند الخلاف.

**59.7 نفاد العرض أثناء الشراء:** تنبيه واضح قبل التأكيد النهائي إذا نفد الحسم المحدود بالسلة؛ لا خصم بدون موافقة الزبون الصريحة على السعر الجديد.

## 60. محرك تسعير مرن يتحكم فيه الأدمن بالكامل

كل الأسعار (اشتراك التاجر، اشتراك الزبون، البانرات، Boost، عمولات مستقبلية) قابلة للتعديل من الأدمن، وممكن تكون **0** (مجانية) لأي طرف. تُخزَّن كـSettings قابلة للتعديل، لا Hardcoded — يسمح بإستراتيجية إطلاق مجانية بالكامل تتحول لتسعير تدريجي بدون تعديل تقني.

## 61. الفترات التجريبية القابلة للتخصيص (Configurable Trial Periods)

الأدمن يحدد فترة تجريبية مجانية منفصلة للتاجر والزبون (أرقام مستقلة). عند الانتهاء: استمرار مجاني تلقائي (إذا السعر 0) أو تحول لحالة "بانتظار الدفع" مع إشعار تذكيري قبل الانتهاء بأيام محددة من الأدمن. كل الأرقام Settings قابلة للتغيير بأي وقت.

---

## 62. آلية الـQR النهائية — تجديد كل 30 ثانية + نسخة احتياطية بدون إنترنت

الكود يتجدد **كل 30 ثانية** (Dynamic Token Refresh). عند عدم توفر إنترنت: **رقم طويل عشوائي (Backup Code، 12-16 خانة)** يظهر تحت الـQR، يكتبه التاجر يدويًا. صالح **لاستخدام واحد فقط**، مدة صلاحية قصيرة. يُسجَّل محليًا وقت الاستخدام (Offline Log)، ويُتحقق منه تلقائيًا من السيرفر فور عودة الاتصال (Offline-to-Online Sync). عند فشل التحقق لاحقًا، تُلغى العملية تلقائيًا مع إشعار للطرفين.

---

## 63. الموافقة اليدوية البسيطة على التاجر + مراقبة صارمة للمحتوى

الموافقة على التاجر تبقى **يدوية وبسيطة** — بيانات أساسية بدون مستندات رسمية بالمرحلة الأولى.

**مراقبة المحتوى (طبقتين):**
1. فلترة تلقائية أولية (Blacklist كلمات مسيئة، قابلة للتحديث من الأدمن).
2. مراجعة يدوية إجبارية لكل صورة قبل النشر للعامة.

أي تعديل لاحق من التاجر (صور/نصوص) يدخل بنفس دورة المراجعة من جديد.

## 64. العملة حسب دولة الزبون (Country-Based Currency)

العملة المعروضة تتحدد تلقائيًا حسب دولة الزبون (رقم الهاتف/الموقع/اختيار يدوي بالتسجيل). الأسعار تُخزَّن بعملة أساسية لكل تاجر (Base Currency per Merchant)، وتُعرض للزبون بعملة بلده مع تحويل تقريبي عند الاختلاف.

## 65. الامتثال لقوانين GDPR للسوق الأوروبي (EU Compliance)

المنصة بالكامل (تطبيق + موقع www.dalilacom.com) تعتمد معايير **GDPR كاملة**:
- موافقة صريحة (Explicit Consent) قبل جمع الموقع/البيانات الشخصية.
- حق الوصول لبياناتي (Right to Access).
- حق الحذف الكامل (Right to be Forgotten)، مع الاحتفاظ بسجلات مالية للفترة القانونية فقط.
- سياسة خصوصية وشروط استخدام بثلاث لغات، مقبولة إجباريًا عند التسجيل.
- تشفير البيانات الحساسة أثناء النقل والتخزين (مرتبط بالقسم 21).
- الموقع الإلكتروني يُبنى بنفس معايير الخصوصية، كواجهة موحدة للسوق الأوروبي.

## 66. فروع التاجر المتعددة (Multi-Branch Merchants)

نموذج معتمد: **حساب تاجر رئيسي واحد + فروع مرتبطة (Parent Merchant + Branch Locations)**.

- حساب دخول واحد يدير كل الفروع.
- كل فرع: عنوان، موقع جغرافي، أوقات عمل، رقم تواصل خاص (أو مشترك).
- الحسم موحّد افتراضيًا، مع إمكانية تخصيص حسم مختلف لفرع معيّن.
- كل فرع نقطة مستقلة بالخريطة والبحث، مع رابط لصفحة المتجر الرئيسي وباقي الفروع.
- كل فرع له تقييماته وتعليقاته الخاصة، مع ملخص عام موحّد بصفحة المتجر الرئيسي.
- DB: جدول `Merchants` (رئيسي) + جدول `Branches` مرتبط بنفس `merchantId`.

## 67. نظام حجز المواعيد (Booking/Appointments)

مهم للأطباء، الصالونات، العيادات، النوادي الرياضية. التاجر يحدد **Availability Schedule** (أيام، ساعات، مدة كل موعد)، وخدمات بمدد مختلفة. الزبون يختار خدمة ويشوف الأوقات المتاحة فقط ويحجز. تأكيد فوري + تذكير تلقائي قبل الموعد + إلغاء/تعديل قبل مهلة يحددها التاجر. التاجر يشوف Calendar View بلوحته ويقدر يحظر وقت يدويًا. الحسم يُطبَّق تلقائيًا على قيمة الخدمة عند الحاجة.

## 68. القائمة الرقمية للمطاعم (Digital Menu via QR)

قائمة طعام رقمية ضمن المتجر الإلكتروني. QR يتولّد تلقائيًا من لوحة التحكم ويُطبع على الطاولات. الزبون يمسحه ليفتح القائمة مباشرة (سعر العضو والحسم ظاهرين). اختياري: طلب مباشر من القائمة (Order للطاولة) أو عرض فقط (Menu View Only).

## 69. عروض الومضة (Flash Deals)

أقصر بكثير من عروض الـStory (القسم 46) — بالساعات مش الأيام. قسم "عروض ومضة" بالـHome مع Countdown Timer واضح. قابلة للربط بعدد استخدامات محدود.

## 70. المواسم والمناسبات (Seasonal Sections)

## 73. الفاتورة الرقمية (Digital Invoice/PDF)
