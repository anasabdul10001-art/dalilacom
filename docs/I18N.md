# Languages

Arabic is the source language of the code (and the default). English ships with it. Every other language is
**one command plus the translations**.

## Add a language

```bash
npm run i18n:add -- de "Deutsch" ltr     # code (2 letters), the language's own name, rtl | ltr
```

It creates and wires up, on every platform, a copy of the English texts as **placeholders** (so nothing breaks
and nothing shows Arabic while you translate):

| Platform | Files | What to translate |
|---|---|---|
| Server | `src/i18n/de.ts` (+ registered in `src/i18n/index.ts`, `src/lib/languages.ts`) | error/status messages, emails, notification texts, the pages the server makes (email verification, Facebook linking), invoice labels |
| Web preview | `public/app/i18n.de.js` (+ a `<script>` in `public/app/index.html`) | `DICT` (keyed texts), `PHRASES` (everything else, key = the Arabic text as shown), `PATTERNS` (texts with numbers/names inside), `WORDS` |
| Android | `res/values-de/strings.xml`, `strings_screens.xml` (+ a line in `ui/i18n/AppLanguages.kt`) | the same keys as `values/` (Arabic) |
| Category names | `prisma/categories.data.ts` — add `tr: { de: { name: "Zahnarzt", syn: "zahnarzt\|zähne" } }` to each node | names + the words people search for (`syn`, separated by `\|`) |

Keep the **keys** (the Arabic sentences, the `{n}` / `$1` / `%1$s` markers) exactly as they are; translate the **values**.
Then:

```bash
npm run i18n:check        # lists what is still missing, and texts still identical to English
npm run prisma:seed       # loads the category translations
```

The language then appears in the language menus of the web preview and the Android app by itself, and the server
answers in it (`?lang=de` or `Accept-Language: de`). Right-to-left languages work the same way (`rtl`).

## How a text reaches the user

* **Apps → server:** every request carries the app's language (`Accept-Language`). The server answers `message` /
  `error.message`, category names, plan names, invoices and server-made pages in that language; the machine-readable
  `error.code` never changes.
* **Account language:** the app saves the language on the account (`PATCH /profile/me { language }`). Push
  notifications and emails are written in it (the inbox keeps the original and is translated for whoever reads it).
* **Web preview:** screens are written in Arabic; for another language the rendered text is translated by lookup
  in `PHRASES` / `PATTERNS` (gettext style), and `DICT` holds the few keyed texts.
* **Android:** all screen texts are string resources (`AppStrings.get(R.string.…)` outside composables).
* **Never translated, on purpose:** what users typed — shop names, product names, descriptions, customer messages.

## The guard

`tests/i18nTooling.test.ts` runs `i18n:check` against the real project. It fails if anyone writes Arabic text for
users in the web app, the server or the Android code without adding its translation — so the languages cannot
silently fall behind.
